SharePoint Access Denied for External Vendors: Transition Internal Accounts to Entra B2B

A practical guide to a confusing identity scenario: an external supplier has a Mattel-native Entra account, but needs to access SharePoint using the supplier's own work identity.

By Rahul Baghel · November 2026 · 8–10 minute read
Scenario: A vendor reports that a SharePoint file or site returns Access denied. The permissions appear correct. When the vendor enters their company email address, Microsoft keeps selecting or redirecting to an account in the resource organization's tenant. The root cause may be the identity used for authentication—not the SharePoint permission assignment.

1. Understand the symptoms

Imagine a supplier employee, Kacper, works for XP Studios and should access Mattel SharePoint with kacper.perkowski@xpstudios.com. In Microsoft Entra ID, however, the account is a native Mattel member with a UPN such as kacper.perkowski@mattelcorp.onmicrosoft.com. The XP Studios address appears only in the account's email/contact attribute.

SharePoint permissions can be correctly assigned to that Mattel account, but the vendor is not necessarily authenticating as the XP Studios identity. Entering an external email address at the sign-in prompt does not convert the Mattel account or change its authentication source.

2. Member, Guest and authentication are not the same thing

Microsoft Entra's UserType describes the user's relationship and permission level in the resource tenant. It does not, by itself, tell you which identity provider authenticates the user.

ConceptWhat it tells youWhat it does not prove
UserType = MemberThe user's relationship/permission classification in this tenant.It does not prove the user authenticates with the host tenant. External B2B members are supported too.
UserType = GuestThe user is classified as a guest in the resource tenant.Changing this value alone does not change the authentication identity.
UPNThe account's sign-in name in the resource directory.A UPN ending in the tenant's onmicrosoft.com domain is a clue, not the only identity property to inspect.
IdentitiesShows the identity provider/sign-in identity associated with the account.Do not infer the provider from the Email contact field alone.

Microsoft distinguishes internal members, internal guests, external guests and external members. An external member can authenticate against another organization's identity provider while having UserType = Member in the resource tenant.

3. Diagnose the account before changing permissions

  1. Open Microsoft Entra admin center → Identity → Users → All users.
  2. Find the vendor's account and open Properties.
  3. Record the complete UPN, User type, Creation type, Email and account source/synchronization status.
  4. Inspect the account's Identities information. For a B2B user authenticated by another Microsoft Entra tenant, the identity provider is typically shown as ExternalAzureAD. An internal account using host-tenant credentials has an identity associated with the host organization.
  5. Check whether the user has a mailbox and whether the account is synchronized from on-premises Active Directory. These details affect the supported transition path.
  6. In SharePoint, open the item's Manage access panel and confirm which directory object has been granted access. Check site, library, folder and item-level permissions as applicable.
Do not stop at the Email field. An external vendor's address stored in mail or Contact Information does not mean the account is already a B2B identity. Confirm the identity provider and how the account authenticates.

4. Why the vendor is sent to the wrong sign-in

In a legacy or manually provisioned setup, an organization may create a cloud account for a supplier and give that person a tenant UPN and password. The vendor's company email may be stored as a contact address. That is an internally authenticated account even though the person is not an employee.

When the vendor opens a SharePoint URL, Microsoft can resolve the sign-in to the existing host-tenant account. Typing the supplier email at the prompt does not automatically replace that account with the supplier's home identity. A browser session containing multiple Microsoft accounts can add confusion, but an InPrivate test only isolates the browser session—it does not repair the underlying identity configuration.

5. Recommended approach: transition the existing account to B2B

If the vendor must authenticate with their XP Studios work identity, use Microsoft's supported Invite internal users to B2B collaboration process for the existing internal user object.

This process is designed to let an existing internal account become a B2B user while retaining the user's object ID, UPN, group memberships and application assignments. When the invitation is accepted, the user signs in to cloud resources with the external identity.

Why this is preferable: It can preserve the existing Entra object and its assignments instead of deleting the account and rebuilding access from scratch. Plan and test the transition carefully because the sign-in method changes.

Before you start

  • Confirm the vendor's correct home-organization sign-in address (for example, kacper.perkowski@xpstudios.com).
  • Confirm the account is eligible for internal-to-external B2B conversion and identify whether it is cloud-only or synchronized.
  • Check the user's mail property. Microsoft requires it to contain the external address that will be used for B2B. If the account already has a mailbox, the property may need to be updated through Exchange admin center; do not blindly overwrite mailbox attributes.
  • Check for onPremisesUserPrincipalName. Microsoft documents that this attribute can prevent the internal-to-external conversion. For synchronized accounts, work with the identity team to assess the supported directory-sync configuration before proceeding.
  • Review Conditional Access, cross-tenant access settings, external collaboration restrictions, licensing and any applications that depend on the current internal credentials.
  • Plan a maintenance window and communicate the sign-in change to the vendor. Keep a record of current group memberships, app assignments and SharePoint access for validation.

Perform the B2B invitation

Follow Microsoft's current procedure in Invite internal users to B2B collaboration. The documented process uses the Microsoft Entra invitation capability (invitation API/PowerShell workflow) and requires both the existing internal user object and the external email address.

  1. Prepare the existing user object and verify its external mail address and conversion eligibility.
  2. Use the supported invitation workflow to invite the existing internal user object to B2B with the vendor's external identity. Do not create a duplicate guest object as a substitute for this existing-object conversion process.
  3. Send the invitation and have the vendor redeem it using the XP Studios identity.
  4. After redemption, verify the user's identity provider and confirm that the account is now using the external B2B authentication path.
  5. Review the account's group memberships, application assignments and SharePoint permissions. Confirm they remain appropriate and that the vendor can access only the resources intended for them.
  6. Test access to the original SharePoint site/file using a fresh browser session and the XP Studios account.
Important: Do not assume that changing UserType from Member to Guest performs this conversion. Microsoft explicitly documents that UserType and internal/external authentication are separate. Also, do not delete the existing account or remove its access before the B2B transition and validation are complete.

6. Share the SharePoint content after identity is corrected

Once the vendor can authenticate with the intended external identity:

  1. Open the SharePoint file or folder and select Share.
  2. For a controlled vendor collaboration scenario, prefer Specific people and enter the vendor's external work address.
  3. Choose the minimum required permission (View or Edit) and send the invitation/link.
  4. Check Manage access to confirm the intended recipient and link permission.
  5. Ask the vendor to open the link while signed in with the same XP Studios identity used to redeem the B2B invitation.

A People in your organization link is not a mechanism for converting an internal account into an external identity. Link type and authentication identity are separate controls. Use the link type that matches your organization's sharing policy and verify the recipient's actual sign-in identity.

7. Validation checklist

  • The vendor's B2B invitation is redeemed.
  • The account's identity provider reflects the vendor's home identity.
  • The vendor can authenticate using the XP Studios work account.
  • The existing object, group memberships and app assignments have been reviewed.
  • The vendor has only the required SharePoint site, library, folder or item permissions.
  • The file opens successfully from a clean browser session.
  • Conditional Access and cross-tenant access policies allow the intended collaboration.

8. When should you not convert the existing account?

If the account is not eligible for the supported internal-to-B2B transition, or the business requires a separate external identity object, work with the identity team to design a controlled migration. That may involve inviting the vendor as a new B2B guest, validating access with the new identity, and only then retiring the old internal account. This is a separate migration path: do not delete the old object until dependencies and access have been mapped.

Key takeaway

When an external vendor receives SharePoint access denied—even though permissions appear correct—check the identity being used to authenticate before repeatedly changing SharePoint permissions. A vendor's external email in the contact field does not make a native account a B2B user. Use Microsoft's supported internal-to-B2B invitation process when the existing internal account must be transitioned, then validate authentication and resource access.
