Automate SharePoint Online Site Inventory with Azure Automation

By Rahul Baghel, creator of M365Buddy

Automate recurring inventory reports for SharePoint Online using Azure Automation, a compatible PowerShell runtime, PnP.PowerShell, certificate-based app authentication, and Microsoft Graph email delivery.

Azure AutomationPowerShell 7.4PnP.PowerShellEntra IDMicrosoft Graph

Maintaining an inventory of thousands of SharePoint Online sites manually can be time-consuming. A scheduled runbook can collect site information, export a report, and send it to the right recipients without requiring an administrator to run the script interactively.

What you’ll build: A scheduled Azure Automation runbook that inventories SharePoint Online sites, creates a report, and emails the output.

Architecture and prerequisites

1Azure AutomationScheduled runbook
2Certificate authEntra app + PnP
3Inventory reportCollect and export data
4Graph emailSend report attachment

The solution uses an Azure Automation Account to host the runbook and runtime environment. An Entra ID app registration authenticates to SharePoint Online with a certificate. A separate Graph email configuration handles report delivery, and a sender mailbox is identified by the MailFrom variable.

  • An Azure subscription and permission to manage Azure Automation resources.
  • SharePoint Online administrative access and an Entra app registration with approved API permissions.
  • A certificate and corresponding PFX material, protected password, and a supported PowerShell runtime.
  • A dedicated sender mailbox and Microsoft Graph configuration if the runbook sends email.

For the fundamentals, see SharePoint Online site inventory with PnP PowerShell and PnP certificate authentication.

1. Create or select an Automation Account

In the Azure portal, open Automation Accounts and create an account or select an existing one. Choose the subscription, resource group, and region according to your organization's standards. The Automation Account hosts runbooks, runtime environments, variables, schedules, and job history.

The workflow diagram above summarizes the main stages. Exact portal labels and module availability can vary by Azure Automation runtime and tenant configuration.

2. Configure the PowerShell runtime

Create or select a PowerShell runtime environment compatible with your script and module versions. The example environment uses PowerShell 7.4. Always verify compatibility against the specific PnP.PowerShell release you plan to deploy; module requirements change over time.

3. Add required packages

Install the modules actually used by the runbook, such as PnP.PowerShell and ImportExcel where applicable. Wait until packages are available before testing. Packages installed on your local computer are not automatically available in Azure Automation.

4. Configure certificate-based app authentication

Register or select an Entra ID application, upload its public certificate under Certificates & secrets, and configure the runbook to access the matching PFX and password securely.

Configuration checkpoint: In Microsoft Entra admin center, open the app registration used by the runbook, upload the public certificate, and confirm the application permissions and admin consent. Keep the private key and PFX password out of source control.

The example script lists SharePoint Sites.FullControl.All and Microsoft Graph Group.Read.All and Mail.Send application permissions. These are not universal minimum permissions. Review the exact calls in your script, grant only what is required, and obtain admin consent where necessary.

Read more: Entra ID app registration for PnP PowerShell certificate authentication and creating a self-signed certificate.

5. Configure Automation variables

Open Variables in the Automation Account and create the variables expected by your runbook. Variable names must match the script exactly.

Variables checkpoint: Store non-secret settings such as tenant ID, client ID, SharePoint admin URL, sender mailbox, and recipient list as Automation variables. Store secrets in encrypted variables or a supported secret store, never as plain text.
VariablePurpose
TenantTenant identifier for authentication.
ClientIdApplication client ID for SharePoint access.
PfxBase64Base64-encoded PFX content used by the script.
PFX PasswordPassword required to open the PFX.
MailClientIdApplication client ID used for Graph email delivery.
MailClientSecretClient secret used by the current Graph email implementation.
MailFromSender mailbox address.
MailToRecipient address or addresses.
Security: Base64 is encoding, not encryption. Protect PFX material, passwords, and client secrets using encrypted Automation variables or a suitable secret store. Restrict access to the Automation Account and review whether Key Vault or managed identity can reduce secret handling.

6. Set up the sender mailbox

Mailbox checkpoint: Use an approved organizational sender mailbox and grant the app only the Graph mail permissions required by your delivery design. Validate the sender address and mail-flow policy with your Microsoft 365 administrators.

Yes—the sender address is part of the configuration. The current script uses MailFrom to specify which mailbox appears as the sender. The mailbox and the app registration are different things:

  • The SharePoint app authenticates the runbook to SharePoint Online.
  • The Graph email app authenticates the send-mail operation.
  • MailFrom identifies the mailbox used as the sender.

A separate licensed user account is not automatically required just to run an Azure Automation runbook. However, this implementation does use a sender mailbox, so the mailbox must exist and the app must be authorized to send from it. Validate the Microsoft Graph permissions, admin consent, and any Exchange application access restrictions in your environment.

7. Import and publish the runbook

Create or import the PowerShell runbook, select the intended runtime environment, and check that all referenced variables and modules are available. Review the script for authentication, logging, error handling, output generation, and email delivery. Save and publish only after the code has been reviewed.

8. Test the job

Start the runbook manually before scheduling it. Inspect the job's status, output, warnings, errors, and logs. A Completed status is a useful first check, but it does not prove that every site was inventoried or that the report email arrived. Validate the report and confirm delivery separately.

9. Schedule recurring inventory

Link a schedule to the runbook and select a cadence that suits your governance needs. Check the time zone and next run time. After the first scheduled execution, verify that the job starts and completes as expected.

10. Validate the report and email

Delivery checkpoint: Test the report with a small recipient list first. Confirm the CSV or Excel attachment opens correctly, the report date is included, and no internal-only fields or unintended recipients are present.

The report columns depend on your script. They may include site name, URL, creation date, last activity, owner details, storage consumption, template or site type, and group privacy details when those fields are collected. Validate the actual output before publishing or distributing it.

Troubleshooting

IssueWhat to check
PnP cmdlets unavailableConfirm the runbook runtime and package availability.
Authentication failureValidate tenant/client IDs, certificate, PFX password, certificate validity, and permissions.
Run fails partway through a large inventoryReview logs and implement resilient token refresh and retry handling where needed.
Missing owner dataCheck whether an owner group exists and handle null owner-group values.
Report created but email failsCheck Graph authentication, MailFrom, MailTo, app permissions, and Exchange restrictions.
Multiple recipients failParse commas, semicolons, or line breaks consistently and create a separate recipient object per address.
Attachment too largeCompress the report or use an approved storage location and secure link; verify the permissions needed for the selected method.

Security and operational checklist

  • Use least privilege and review high-impact application permissions.
  • Protect certificate material, passwords, and client secrets.
  • Monitor certificate and secret expiry dates.
  • Keep module versions and runbook changes under change control.
  • Review failed jobs and validate report completeness.
  • Confirm recipients and report-retention requirements.

Conclusion

Azure Automation can reduce manual effort by running SharePoint Online inventory reporting on a recurring schedule. The key is to validate the entire process—from authentication and site collection through report generation and email delivery—before relying on it for ongoing governance.
